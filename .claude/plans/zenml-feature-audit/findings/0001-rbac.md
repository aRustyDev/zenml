## 4. OSS degradation

**Lost:**

- Per-resource authorization. All 9 guards permit. A user with any valid token can read/update/delete every project-scoped and global resource the API exposes.
- Field-level redaction. `dehydrate_response_model` (`utils.py:95`) normally blanks sub-resources the caller can't read and stamps `permission_denied=True` via `get_permission_denied_model` (`utils.py:214-230`); in OSS `:110` returns the model whole.
- Resource sharing. `POST /users/resource_membership` is not even registered — the router block is behind `if server_config().rbac_enabled:` at `users_endpoints.py:696`. Its `team_id` parameter (`:712`) is doubly dead: **OSS has no Team entity at all** (no `TeamSchema`/`TeamResponse` anywhere in `src/zenml`; `team_id` survives only in historical migrations, e.g. `migrations/versions/alembic_start.py:174`).
- List scoping. `get_allowed_resource_ids` returns `None` (`utils.py:381-382`), so `configure_rbac` (`filter.py:829`) is never given an ID allowlist at the 8 call sites that use it (`projects_endpoints.py:268,276`, `service_connectors_endpoints.py:161,213`, `runs_endpoints.py:272`, `run_wait_conditions_endpoints.py:111`, `steps_endpoints.py:105`, `users_endpoints.py:124`).

**Substitute: a single boolean column.** `UserSchema.is_admin` (`zen_stores/schemas/user_schemas.py:92`, default `False`) surfaced as `UserResponse.is_admin` (`models/v2/core/user.py:172,433-439`), enforced by `verify_admin_status_if_no_rbac()` (`zen_server/utils.py:793-822`). Its shape is the tell — it *only* acts when RBAC is off (`:810`), raising `IllegalOperationError` → 403 (`zen_server/exceptions.py:74`) when `admin_status is False` (`:816-820`).

14 call sites, all in three routers (plus 3 import lines and the definition — `grep -rn` shows 18 lines total):

| Router | Lines |
|---|---|
| `users_endpoints.py` | `:173`, `:215`, `:319`, `:370`, `:505` |
| `service_accounts_endpoints.py` | `:113`, `:219`, `:257`, `:315`, `:429`, `:480`, `:510` |
| `secrets_endpoints.py` | `:268`, `:302` |

Plus one hand-rolled equivalent for server settings at `server_endpoints.py:207-218`, and self-scoping of user listing at `users_endpoints.py:123-127`.

**So OSS authorization = admin / not-admin, covering 14 call sites.** Stacks, pipelines, runs, artifacts, models, flavors, code repos, triggers, tags, connectors: no check at all.

## 5. Self-host path

Tier A: nothing to enable. Writing an OSS RBAC backend means:

1. A class implementing 4 abstract methods (`rbac_interface.py:29,45,65,85`) — `check_permissions`, `list_allowed_resource_ids`, `update_resource_membership`, `delete_resources`. Set `ZENML_SERVER_RBAC_IMPLEMENTATION_SOURCE=<dotted.path>` (or Helm `zenml.auth.rbacImplementationSource`, `helm/values.yaml:297`). The loader validates the base class (`zen_server/utils.py:149-151`), so a third-party class is accepted — there is no Pro-only assertion on the loader path.
2. A persistence layer for grants. There is none in OSS: no table, no migration, no model. `update_resource_membership` takes `user_id` *and* `team_id` (`rbac_interface.py:70-71`) but OSS has no teams — a self-host implementation would have to invent both the grant table and the group concept.
3. Correct semantics for `list_allowed_resource_ids`'s `(full_access, ids)` tuple (`rbac_interface.py:56-61`), which feeds SQL filters — getting this wrong leaks rows rather than erroring.
4. `is_project_scoped()` (`models.py:83-102`) must be honoured or `Resource`'s validator rejects the object (`models.py:160-185`).

Sizing: ~25 `ResourceType` values × 9 `Action` values, plus the schema mapping at `utils.py:692`. The interface is small; the *policy model* is the whole job. Call it a multi-week piece of work, plus a migration, plus an admin UI/CLI that does not exist.

⚠️ **Adding a `ResourceType` requires touching four places in lockstep**: the enum (`models.py:50`), the project-scoping list (`models.py:89`), the schema mapping (`utils.py:718-756`), and — if it needs metering — `DEFAULT_REPORTABLE_RESOURCES` (`constants.py:465`).

## 6. Blast radius

Import fan-in (counted with `grep -rln` over `src/zenml --include="*.py"`):

| Module | Importers |
|---|---|

| `rbac.endpoint_utils` | 31 files (30 routers + `utils/logging_utils.py:575`) |
| `rbac.utils` | 26 files |

Cross-module hops that matter:

- **Store class swap.** `base_zen_store.py:157-162` → `RBACSqlZenStore`. Every ZenML *server* runs the RBAC store subclass; it overrides `batch_create_tag_resource` (`:50`), `batch_delete_tag_resource` (`:75`), `_get_or_create_model` (`:96`) and pulls the feature gate in (`:32-35`). A change to `verify_permission*` therefore changes tag and model creation behaviour on every deployment, Pro or not.
- **`utils/logging_utils.py:575`** imports `rbac.endpoint_utils` — a `zen_server` dependency reaching into `zenml.utils`, i.e. outside the server package. Worth flagging against the repo's own import rule in `src/zenml/zen_server/AGENTS.md`.
- **Feature gate coupling.** `rbac/endpoint_utils.py` is the only place RBAC and metering are fused (`:102,107,188,195`), so the two gates are not independently swappable via the CRUD wrappers.
- **Ownership shortcut.** `has_permissions_for_model` (`utils.py:194`) returns `True` immediately for `is_owned_by_authenticated_user` (`utils.py:597`) *before* consulting RBAC (`:204-205`) — owner-bypass is unconditional, Pro included.
- **Vocabulary trap.** `ResourceType.PIPELINE_SNAPSHOT = "pipeline_deployment"` (`models.py:62`) — the wire value, the Pro control plane's key, and the grep target all differ from the symbol. `ResourceType.DEPLOYMENT = "deployment"` (`:64`) is a *different*, unrelated concept.
